# Environment and domain conventions

## Ownership

The existing Virginia deployment is preserved. This continuation does not change DNS, registrars, mail settings, WAF or CDN policies. Domain records below are examples for a separately owned project; confirm each provider's current required targets before applying. Registration selection should compare renewal price, transfer policy, security/MFA, DNSSEC and support rather than only first-year promotions.

| Environment | Example                                  | Secret source                                          |
| ----------- | ---------------------------------------- | ------------------------------------------------------ |
| Development | localhost:3000 / localhost:3300          | Private local .env, never committed                    |
| Preview     | Provider-generated unique deployment URL | GitHub preview Environment and Vercel preview settings |
| Staging     | staging.example.com                      | Separate staging Environment                           |
| Production  | example.com or app.example.com           | Protected production Environment                       |

PR preview URLs are immutable/provider-generated by default. A custom pr-123.preview.example.com pattern requires explicit aliases, wildcard DNS/TLS and cleanup; it does not follow automatically from a YAML filename. Do not share authentication cookies across these hosts.

## Web DNS and TLS examples

For Vercel, add and verify the domain in that specific project, then use the exact A/CNAME/TXT values the dashboard supplies. Do not hardcode a historical Vercel IP into a universal template. A typical subdomain record is CNAME app -> <project-specific Vercel DNS target>. A verification record is TXT <provider-specified-name> -> <verification-token>. Tokens shown here are placeholders, not credentials.

For a standalone host, a typical A record points app to the authorized server IPv4. Caddy can issue/renew an ACME certificate once DNS and network reachability are correct. Vercel manages its own certificates; the user does not run Caddy or Let's Encrypt on Vercel. Preserve unrelated records and check CAA restrictions. Official sources: [Vercel domains](https://vercel.com/docs/domains), [Caddy automatic HTTPS](https://caddyserver.com/docs/automatic-https).

## Transactional email policy templates (not installed)

| Type                | Name                                   | Placeholder value                              |
| ------------------- | -------------------------------------- | ---------------------------------------------- |
| MX                  | mail.example.com                       | <priority> <mail-provider-target>              |
| TXT / SPF           | mail.example.com                       | v=spf1 include:<provider-spf-domain> -all      |
| CNAME or TXT / DKIM | <selector>._domainkey.mail.example.com | <provider-selector-target-or-public-key>       |
| TXT / DMARC         | _dmarc.mail.example.com                | v=DMARC1; p=none; rua=mailto:dmarc@example.com |

Use only one SPF record per sending hostname. Merge approved senders, validate SPF lookup limits, verify DKIM alignment and review DMARC aggregate reports before moving to quarantine/reject. MX is for receiving mail; it is not universally required for an outbound-only transactional provider. The rua address must be real and authorized. No mail SDK, service or DNS changes are part of this project.

## Future product integration points

Backend-only placeholders may include STRIPE_SECRET_KEY, RESEND_API_KEY and S3_SECRET_ACCESS_KEY. Browser-safe publishable keys require explicitly named public prefixes and a privacy review. Supabase/Firebase/Clerk/Auth0, payments, object storage, queues and transactional mail SDKs are intentionally absent from this engineering continuation. Optional Neon CI branching is deferred until the core milestones pass.
